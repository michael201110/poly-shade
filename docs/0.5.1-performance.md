# PolyShade 0.5.1 performance pass

## Baseline and reproduction

Baseline: **0.5.0**, clean `main` at `e62b9d3cfbb207039e7ef8c8e1318bd156931601`.
The archived 0.5.0 bundle is unchanged. Windows laptop, NVIDIA T500 4 GB,
driver 573.91 (32.0.15.7391), Edge 155.0.4283.45, enhanced Three 0.181.2.
Screen 1920×1080, DPR 1. Live output 1327×947, internal 664×474.
User settings: Golden Hour (`cinematic`), SGSR2 Compute, Performance 50%.
No shadow resolution, effect strength, sample count, geometry, replay sample,
interpolation or visibility policy was reduced.

The current architecture was inspected before profiling: 0.5.0 already uses
one WebGPU device for the scene, effects and actual Qualcomm SGSR2 Compute.
PolyBot 0.1.48 supplies worker-interpolated packed instances through optional
API v1; eleven native geometry/material groups, full suspension morphs,
native skid rings and instanced velocity feed that same renderer. This pass
does not introduce another canvas, worker renderer or per-ghost scene tree.

Raw CPU/GPU pass distributions, upload/allocation/submission counters,
settings, resolutions, resource formats/usages, replay packet hashes and
hardware samples are in [measurements.json](verification/0.5.1/measurements.json).
Timestamp profiling is asynchronous and opt-in; no normal-frame readback or
GPU fence was added. GPU timestamps have coarse 65.536 µs quantization here.

Two fixtures were used:

- Live Simple Track: complete saved attempts, evenly selected over training
  steps, identical packet SHA256s before/after. 1/25/50/100/250/500 cars;
  5 s warmup, restart, 1 s settle, 15 s sampling, looping. All requested cars
  are loaded, full geometry; natural replay finish/coast/disappearance and
  existing worker culling still apply. “500” is capacity, not a promise that
  all 500 overlap every measured frame. Colours are green, opacity 100%.
- Fresh headed Edge, fixed offline Summer 1 view at 1280×720: shared camera,
  fixed green/white paint (fresh native profiles randomize paint), 3 s warmup,
  10 s sampling per full-quality setting. Detailed CPU method instrumentation
  adds overhead: compare those CPU results only within that fixture. Live
  results use lighter instrumentation. Cloud time is fixed only for paired
  screenshots, not performance samples.

System load and driver clocks vary on a power-limited laptop. These are
sequential observations, not randomized controlled GPU throughput trials.
Small GPU differences are mixed; this report does not claim a win everywhere.

## What actually cost time

1. **Redundant GPU uploads, especially skid marks.** Three r181 uploads
   `DynamicDrawUsage` attributes on every draw even when their version is
   unchanged. With no pending update range, the 500-car skid corner buffer
   uploaded **95,904,000 bytes** in one call. A 2.5 s trace found 151 writes
   totalling 191.9 MB to that buffer, including two complete uploads. This
   caused bandwidth pressure and large main-thread spikes.
2. **Velocity history repacking.** Every geometry group rebuilt interleaved
   current/previous matrices and morph weights on the CPU, then uploaded them.
3. **Duplicate velocity vertices.** Native full car geometry contains separate
   vertices for hard normals/material boundaries. Velocity only uses positions
   and four morph deltas, so many of those vertices were identical for its job.
4. **Repeated fixed setup.** Scene discovery, repeated shared-material updates,
   texture views and post/SGSR2 bind-group descriptors produced avoidable CPU
   work. Profiling also confirmed expensive Capture volumetrics when the sun
   is visible; these were not silently disabled.

## Implemented changes

### Instance uploads and history

Owned instance attributes now use version-driven uploads. Every transform
packet still marks matrices dirty; colours, opacity and suspension weights
mark dirty only when their exact float values change. Skid updates retain the
union of all pending worker ranges until Three consumes them, including
multiple packets between draws. Ring reset and overwrite behavior is retained.
`StaticDrawUsage` is a Three upload policy here, **not frozen animation**.

Velocity consumes contiguous matrix/weight arrays directly. Queue-ordered GPU
copies preserve the last rendered frame in persistent history buffers. First
frame, camera reset, disappearing/reappearing batches and suspension weights
retain the previous semantics. No CPU readback or synchronization is involved.

Velocity geometry welds **bit-identical** position plus all four morph deltas,
including signed zero; an index buffer retains every original triangle and
its order. Actual native prototype vertices fall **5,106 → 1,280**, with the
same 1,702 prototype triangles. Full colour/shadow meshes are untouched;
the full car still has 3,102 triangles including repeated wheel geometry.

### CPU and resource reuse

- Native topology events invalidate a persistent discovery index. Live world
  matrices, ancestor visibility, lights and material values are still read
  every frame. Older native implementations conservatively rescan. Capability
  detection inspects the native factory, without constructing game objects or
  consuming the game's random/ID stream. Listener cleanup follows track changes.
- Shared geometry/material synchronization runs once per frame; live inspector
  edits still refresh next frame. Visited/light sets and background colour are
  reused. This is not an immutable-material assumption.
- Post passes cache default texture views and bindings by actual resource
  identity, with resize invalidation and writable-target alias protection.
  SGSR2 caches both history ping-pong groups. Rigid velocity bindings persist.
- Empty rigid velocity passes are omitted. Active blur/rays/lens algorithms
  remain unchanged; exact-zero contributions return before unnecessary
  samples/exponentials. No active sample count was reduced.

Fixed-view steady state went from about **9 bind groups and 30 texture views
per frame** to **0 new groups and 1 swapchain view**, with zero stable-frame
texture allocations/resizes. Existing target formats, scales, lifetime,
temporal histories and shadow-map quality remain unchanged. Resource inventories
are included in the raw reports; no reduced-precision target substitution was
made. The native scene mirror still updates matrices and Three still allocates
some render bookkeeping: this is not a claim of an allocation-free engine.

## Memory and correctness

500-car JS heap snapshot **467 → 451 MB**; during the sustained candidate run
heap **431 → 375 MB** after normal GC. Snapshots across smaller cases fluctuate
with GC, so they do not establish an allocation-rate reduction. Shared replay
canonical data remains 34.1 MB; native prototype geometry 82.5 KB; the full
95.9 MB skid ring capacity is retained. Main savings are transient repacking,
binding descriptors and upload traffic, not fewer replay samples or skid slots.
At 500 cars available system RAM was 1,042 → 882 MB; baseline paging median
18 input pages/s, candidate 0. Other applications contribute to RAM pressure.

The interop remains renderer-only. This patch changes no PolyBot code, worker
interpolation, replay clock, recording, bridge physics command, training data,
model, reward or learner. Benchmark export uses the existing replay serializer
and rejects non-render operations. There is no training or physics API in the
new renderer code. Normal PolyShade use without PolyBot remains supported.

## Reproduction commands

Use `POLYSHADE_HEADED=1` for the real Edge checks. `npm ci` installs the pinned
dependency tree. The five required release commands are `npm ci`,
`npm run check`, `npm run verify:webgpu`, `npm run verify:visual` and
`npm run verify:upscaling`. Additional fidelity checks:

```powershell
node scripts/verify-post-equivalence.mjs
node scripts/verify-swarm-equivalence.mjs
$env:POLYSHADE_BUNDLE='0.5.1/main.mod.js'
node scripts/verify-performance-visual.mjs
$env:POLYSHADE_PROFILE_LABEL='candidate'
node scripts/profile-renderer.mjs
```

For the baseline fixed-view sweep, set `POLYSHADE_BUNDLE=0.5.0/main.mod.js`.
For a matching camera, point `POLYSHADE_CAMERA_FILE` at the baseline report.
Use `POLYSHADE_CASES` to select comma-separated case names. Run GPU fixtures
one at a time, with other rendering tabs paused. `scripts/sample-system.ps1`
collects independent CPU/RAM/paging samples; `nvidia-smi` provides device data.
`scripts/export-swarm-benchmark.py` runs in PolyBot's Python environment,
using `--run <visual_replays>` and `--output <temporary-folder>`; it exports
complete selected attempts and checksums without starting a simulator/learner.

## Remaining costs

At 500 cars, cascaded dynamic shadows are now a larger GPU cost than velocity
(candidate medians ~3.93 ms shadows, ~0.46 ms swarm velocity). Full-resolution
SGSR2 upscale and grading remain visible costs. Three's scene/render-list/UBO
work and full ring capacity still exist. Capture's visible volumetric sunlight
can dominate at higher pixel counts. Shared-memory worker transport and further
shadow/geometry changes need separate profiling and fidelity proof; none are
required for the measured ~60 FPS target.
